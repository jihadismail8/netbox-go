- [ADR 0003](../adr/0003-unified-authentication-and-authorization.md)
  requires REST token credentials and browser sessions to resolve through the
  same application identity path while keeping transport credential mechanics
  separate.
- The implementation plan declares only the
  [`Authorization: Token` REST path](../IMPLEMENTATION_PLAN.md#identity-and-system-contract)
  and requires unknown, expired, revoked, write-disabled, source-restricted,
  and inactive-owner token conditions to fail closed.
- [I2](CW1-V1-02-I2.md) accepted the pinned single-value REST `Token` byte
  grammar, duplicate-field rejection, transport-neutral token outcomes, exact
  baseline 403 details, direct-peer evaluation, and unary gRPC behavior. It
  deliberately applied the parser only to `BaselineMiddleware()` and preserved
  the identity extension's then-current parser for later review.
- [I3](CW1-V1-02-I3.md) accepted valid-session-first arbitration. A valid
  session ignores Authorization, including malformed or duplicate values;
  session CSRF denial and infrastructure failure never fall through. Only the
  typed Missing, Unknown, Expired, and InactiveOwner session outcomes may reach
  the transport-specific token parser.
- [I4](CW1-V1-02-I4.md) preserves the winning credential's browser-session or
  API-token provenance through password change. The adapter must never infer
  provenance after authentication.

  case-sensitive `Token ` prefix, and applies Unicode-aware `TrimSpace` before
  authentication. It therefore selects the first duplicate field, can alter
  an opaque UTF-8 credential, and lets malformed shapes reach token lookup.

  grammars differ and that the extension selects the first duplicate value.
  I6 must explicitly supersede only those deferred assertions. Historical I2,
  I3, and I4 packets and evidence remain byte-unchanged and continue to attest
  only their recorded revisions and digests.

## Proposed policy for owner review

Use one exact REST `Token` parser for both baseline and identity-extension
middleware. This deliberately adopts I2's accepted NetBox/DRF-compatible byte
grammar for the extension rather than creating a second stricter project
dialect. Baseline rendering remains unchanged; only the extension parser and
its already-generic response boundary are affected.

Token parsing occurs only after I3 session-first arbitration permits token
fallback. The parser:

- reads `request.Header.Values("Authorization")` and requires exactly one
  field value;
- splits only on Python bytes-whitespace bytes `0x09` through `0x0d` and
  `0x20`, never Unicode whitespace;
- compares `Token` with ASCII-only case folding;
- accepts leading, trailing, and repeated permitted byte separators;
- requires exactly one nonempty credential field;
- rejects more than two byte fields before UTF-8 validation;
- validates UTF-8 only on the single credential field;
- passes the accepted credential to `AuthenticateToken` byte-for-byte without
  trimming, normalizing, case folding, or reconstruction; and
- rejects every malformed or duplicate shape before hashing, lookup, touch,
  peer evaluation, password-provenance context, or protected handler entry.

NBSP and other Unicode whitespace are not separators. `Token` followed only by
NBSP is an unsupported/no-scheme shape. Valid UTF-8 non-ASCII bytes inside the
credential, including an NBSP suffix, remain opaque credential bytes and are
looked up unchanged. CR/LF-bearing wire requests remain `net/http` transport
rejections; parser-only tests may cover byte semantics without constructing an
illegal HTTP request.

The extension never exposes baseline parser details or token state. Every
missing, malformed, duplicate, unsupported, unknown, revoked, expired,
inactive-owner, source-unavailable, or source-denied credential returns HTTP
401 with the exact body
`{"detail":"Authentication credentials were not provided."}`. It emits no
`WWW-Authenticate`. Write denial remains HTTP 403 with
`You do not have permission to perform this action.` Infrastructure failure
remains HTTP 500 with `An internal error occurred.`

This packet does not alter the separate method classifiers:

- session-CSRF-safe: `GET`, `HEAD`, `OPTIONS`, and `TRACE`;
- token-read-safe: `GET`, `HEAD`, and `OPTIONS`; and
- every other token method, including `TRACE`, `PROPFIND`, and unknown methods,
  requires write permission.

Direct `RemoteAddr` remains the only client source. Forwarded headers and
trusted-proxy policy remain a later child.

must not render request or credential material.

| Invalid UTF-8 credential                                | generic 401                                            | zero / zero                                            |

## Proposed implementation shape

After activation, make only this vertical change:

1. Rename or extract the existing byte parser as a private shared REST Token
   helper without changing baseline acceptance or detailed baseline rendering.
2. Replace extension `Header.Get`/prefix/Unicode-trim parsing with
   `Header.Values` and that helper.
3. Discard parser-specific detail at the extension boundary and retain its
   exact generic 401 response.
4. Pass an accepted credential unchanged into the existing
   `AuthenticateToken` operation and set API-token password provenance only
   after successful authentication.
5. Replace only the two accepted residual assertions that deliberately froze
   the old extension grammar and duplicate-first behavior; retain all other
   I2-I4 tests as immutable regression prerequisites for their accepted slices.

No new application port, transaction, store call, table, migration, route,
public response field, or frontend behavior is permitted.
