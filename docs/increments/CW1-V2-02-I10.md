Additional field rules:

- DeviceType, DeviceRole, Site, and Rack inputs stay inside the profile's
  positive numeric-ID envelope. Numeric strings, nested dictionaries, slug
  lookup, and generic relationship grammar are not promoted here.
- `name`, `serial`, `asset_tag`, `description`, and `comments` use the pinned
  serializer's whitespace trimming. Only the declared blankable fields accept
  stored blank. Name and asset tag preserve the distinction between SQL null
  and blank.
- `status` accepts exactly `offline`, `active`, `planned`, `staged`, `failed`,
  `inventory`, or `decommissioning`. `face` accepts blank, `front`, or `rear`.
  `airflow` accepts blank or exactly `front-to-rear`, `rear-to-front`,
  `left-to-right`, `right-to-left`, `side-to-rear`, `rear-to-side`,
  `bottom-to-top`, `top-to-bottom`, `passive`, or `mixed`. Choice values are
  not whitespace-trimmed.
- Create resolves DeviceType airflow inside the same application-owned
  transaction. Omitted, REST-null, or blank airflow inherits that DeviceType's
  current airflow. Update null/blank clears to stored blank and does not
  re-inherit. Fixtures prove inheritance with zero InterfaceTemplates and make
  no template-snapshot claim.
- PUT omission resets only `rack`, `position`, and `face`. Required
  `device_type`, `role`, and `site` remain required; all other optional
  omissions preserve current state. PATCH preserves every omitted field.
- Position tests use known-valid unpositioned or isolated concrete values.
  Range, half-unit, Rack bounds, face/rack coupling, zero-U, occupancy, and
  overlap rules remain wholly in `CW1-V2-03`.
- Name and asset-tag uniqueness remain open. Fixtures use null or unique values
  and make no uniqueness, conflict, locking, or concurrency claim.
- Combined violations return once in deterministic owned-field order without
  mutating the aggregate or discarding valid sibling-field intent.
- POST retains add permission and PUT/PATCH retain change permission; I10 uses
  authorized principals and does not expand the RBAC matrix.
- Every mutation uses one application-owned PostgreSQL transaction.
  Relationship resolution, authorization, normalization, validation,
  persistence, DeviceType-airflow lookup, and exactly one typed Device object
  change share that transaction.
- I10-owned command, relationship, or scalar validation rejection leaves the
  loaded aggregate, timestamp, repository mutation count, template-list count,
  interface-create count, and object-change count unchanged. Placement-failure
  mutation behavior remains outside I10.
- Repository or recorder failure leaves the durable Device row and object
  changes unchanged through the application-owned transaction.

Generic coercion, malformed UTF-8, byte-exact framework diagnostics, empty
PATCH, alternate relationship input, diagnostic multiplicity, and template
failure injection remain out of scope. PATCH omission tests include a concrete
sibling field.
