## Required observable contract

### Create, replace, and update

| Field         | POST omitted   | PUT omitted    | PATCH omitted | Explicit `null`          | Explicit `""`            |
| ------------- | -------------- | -------------- | ------------- | ------------------------ | ------------------------ |
| `name`        | required error | required error | preserve      | reject: may not be null  | reject: may not be blank |
| `slug`        | required error | required error | preserve      | reject: may not be null  | reject: may not be blank |
| `status`      | default active | preserve       | preserve      | reject: may not be blank | reject: may not be blank |
| `facility`    | default `""`   | preserve       | preserve      | reject: may not be null  | clear to `""`            |
| `description` | default `""`   | preserve       | preserve      | reject: may not be null  | clear to `""`            |
| `comments`    | default `""`   | preserve       | preserve      | reject: may not be null  | clear to `""`            |

Additional scalar rules:

- name and slug are trimmed, required nonblank strings with a maximum of 100
  Unicode code points;
- slug uses the pinned ASCII `^[-a-zA-Z0-9_]+$` grammar and is never generated
  by the REST API;
- status is one of `planned`, `staging`, `active`, `decommissioning`, and
  `retired`; it is not whitespace-trimmed before choice validation;
- the pinned custom choice converts status null to blank, so status null and
  blank share the baseline blank violation;
- facility and description are trimmed and limited to 50 and 200 code points
  respectively; comments is trimmed with no declared maximum;
- every rejected POST/PUT/PATCH leaves the Site row, `created`,
  `last_updated`, and object-change count unchanged; and
- each successful PUT/PATCH writes the intended state and exactly one object
  change in the existing application-owned transaction.

Generic DRF numeric-to-string coercion, malformed UTF-8 parser behavior, and
byte-exact generic character-field diagnostics are not promoted by this
bounded presence increment. They remain visible exact-REST differential work;
tests here pin safe field-specific reasons and the exact status choice behavior
without claiming a retained T2 boundary.

### API, gRPC, and Vue contract

- Resource metadata distinguishes response nullability from POST, PUT, and
  PATCH required/null/blank rules.
- Generated OpenAPI uses `SiteCreate`, `SiteReplace`, and `SiteUpdate`. Create
  and replace require `name` and `slug`; update requires neither. All six
  write scalars are non-nullable. Only `facility`, `description`, and
  `comments` are blankable.
- The Site response advertises nullable baseline timestamps but non-null name,
  slug, status, facility, description, comments, display, URL, ID, and counts.
- REST preserves omitted, null, blank, and concrete field states and retains
  the exact status choice envelope on responses.
- gRPC optional scalars preserve omission and blank. For PATCH, a FieldMask
  path with the scalar absent represents explicit null intent and reaches the
  same field-specific application validation. Optional proto scalars cannot
  separately express POST/PUT null; this bounded increment does not redesign
  or regenerate protobufs.
- Vue initializes create status to active; name, slug, and status remain
  required; facility, description, and comments remain optional.
- Vue create serialization preserves omitted, blank, and concrete values.
  Edit hydration retains a private original scalar snapshot so unchanged
  scalars are omitted from PATCH, while cleared optional text sends `""`.
- Vue consumes field-scoped server validation and does not own authorization or
  a second business-error taxonomy.
