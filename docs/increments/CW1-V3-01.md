## Current defect

- Canonical HTTP maps both `GET /health` and `GET /ready` to Sponge's static
  `CheckHealth`, so PostgreSQL loss cannot make readiness fail.
- Runtime gRPC registers `health.NewServer()`, whose empty-service state begins
  and remains `SERVING` without checking PostgreSQL.
- HTTP and gRPC construct their runtime independently and receive no explicit
  shared operational readiness dependency.
- Existing tests require static 200/SERVING behavior and do not prove
  success → loss → recovery.
- The canonical router correctly omits a dedicated `/ping`; the frozen
  runtime-disabled legacy router still contains historical probe wiring and
  is not an implementation target.

## Required observable contract

### Shared dependency check

- Introduce a precisely named platform-readiness package with a narrow
  context-aware `Pinger` contract equivalent to
  `PingContext(context.Context) error` and a transport-neutral readiness
  checker.
- Production composition obtains the existing initialized GORM handle's
  `*sql.DB` once, constructs one checker, and injects that same checker into
  HTTP and gRPC.
- Each check calls PostgreSQL once. There is no cached/sticky ready state,
  background goroutine, service-owned reconnect policy, or schema/query
  inspection.
- Each check derives a maximum one-second deadline with
  `context.WithTimeout`; an earlier caller cancellation/deadline wins.
- Nil/unconfigured dependencies, inability to obtain `*sql.DB`, cancellation,
  timeout, and ping error fail closed. Public adapters never expose or log the
  raw cause, DSN, database/dependency hostname, credential, or configuration.

### HTTP liveness and readiness

| Request | Dependency state | Required response |
| ------- | ---------------- | ----------------- |
| `GET /health` | any state while HTTP serves | `200`, JSON `{"status":"UP","hostname":<current hostname>}` |
| `GET /ready` | PostgreSQL ping succeeds | `200`, the same `UP` JSON shape |
| `GET /ready` | nil, cancelled, timed out, or ping fails | `503`, JSON `{"status":"DOWN","hostname":<current hostname>}` |

- Both routes remain narrow public process probes and expose no Managed Object
  or dependency-error detail.
- `GET /health` never calls PostgreSQL.
- `/ready` checks on every request, so deterministic success → loss → recovery
  is visible immediately.
- No dedicated `/ping` route or SPA bypass is added.

### gRPC health

- The existing public standard `grpc.health.v1.Health` registration remains.
- `Health/Check` with empty service name performs one readiness check.
  Successful PostgreSQL ping returns `SERVING`; any fail-closed state returns
  `NOT_SERVING`. Both are successful gRPC responses, as required by the
  standard health protocol.
- A non-empty service name remains unsupported and returns `codes.NotFound`
  without probing PostgreSQL. V3-01 makes no per-service readiness claim.
- `Health/Watch` returns `codes.Unimplemented` immediately. grpc-go documents
  this as an unsupported Watch result that clients must not retry. A client may
  invoke unary `Check` separately, but no automatic fallback is claimed.
  Continuous streaming monitoring would require a separately reviewed
  lifecycle/polling contract and is not invented here.
- grpc-go `v1.67.1` has no health `List`; no toolchain/dependency upgrade or
  fictional List contract is allowed.
- The existing unauthenticated unary health exception remains exact. No other
  protected method is made public.
