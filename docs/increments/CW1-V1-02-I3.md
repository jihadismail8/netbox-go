## Authority and classification

The authority order is the execution playbook, accepted project rules, the
pinned NetBox/Django/DRF source, accepted profile metadata, and only then
current implementation/tests. Generated output and current drift do not
override those sources.

Pinned baseline facts:

- NetBox configures DRF `SessionAuthentication` before its Token
  authentication class.
- DRF stops at the first successful authenticator and aborts on an
  authentication exception.
- A valid session is therefore authoritative even when Authorization is
  present; a session CSRF failure never falls through to a token.
- An absent, unknown, expired, or inactive-owner session yields no principal
  and may fall through to the token authenticator.
- Django's CSRF-safe methods are `GET`, `HEAD`, `OPTIONS`, and `TRACE`.
- DRF's token-safe methods are only `GET`, `HEAD`, and `OPTIONS`.
- The pinned NetBox session cookie and the generated OpenAPI both use
  `sessionid`.

Classified Go browser-extension rules:

- `/api/auth/login/`, `/api/auth/logout/`, and `/api/auth/csrf/` retain their
  declared JSON/204 extension shapes rather than copying NetBox HTML redirects.
- The browser session expires at a fixed, non-sliding 12-hour boundary.
- The session cookie is `sessionid`; the previous `netbox_session` runtime and
  compatibility-harness expectation is implementation drift corrected here.
- CSRF uses one readable literal double-submit cookie/body/header value; it
  does not adopt Django's masked-token representation in this increment.
- The session-bound CSRF value is deterministically derived with
  HMAC-SHA-256, keyed by the exact ASCII bytes of the Base64 raw-URL encoded
  256-bit random session secret and the exact ASCII domain tag
  `netbox-go/browser-csrf/v1`, then Base64 raw-URL encoded. Only the SHA-256
  digest of that public CSRF value is persisted.
- The deterministic derivation is a security construction for safe concurrent
  bootstrap recovery. It neither exposes the HttpOnly session secret nor
  creates a second reusable database credential.
- Literal cookie/header equality, session-only POST logout, fixed cookie flags,
  and duplicate-input rejection are secure extension behavior.

Origin and HTTPS Referer verification, Django masking, NetBox's configurable
14-day/sliding session policy, stale-cookie cleanup, and full browser execution
remain explicit residual work. I3 must not claim full Django CSRF parity.

## Outcome

Deliver one coherent browser-session vertical slice:

1. Application session failures have typed, transport-neutral causes and keep
   infrastructure failures distinct.
2. Valid sessions take precedence over Authorization on baseline and identity
   routes; only expected invalid-session states may fall through to tokens.
3. Cookie-authenticated mutations require an exact, unique CSRF cookie/header
   pair and stored session binding.
4. Every fresh or replacing login revalidates identity in one application
   transaction, rotates server-owned material, and rolls back atomically.
5. Logout is session-only, CSRF-protected, transactionally revalidated, and
   clears cookies only after committed revocation.
6. CSRF bootstrap cannot poison an active session and can atomically converge
   a pre-I3 session row onto the deterministic derived CSRF digest.
7. Session cookies use the declared `sessionid` name, exact flags, fixed
   lifetime, and safe tombstone shape.
8. Real PostgreSQL evidence proves rollback and the stale-password race on an
   owned disposable schema.

## Application contract

### Typed session outcomes

Add `SessionCredentialFailure` with these transport-neutral kinds:

```text
SessionCredentialFailureMissing
SessionCredentialFailureUnknown
SessionCredentialFailureExpired
SessionCredentialFailureInactiveOwner
```

The outer error remains the generic `Unauthenticated` application error. The
typed cause contains no secret or hash. Exact classification:

| State                                    | Reason          | Typed kind    | Required effects                     |
| ---------------------------------------- | --------------- | ------------- | ------------------------------------ |
| Empty session secret                     | unauthenticated | Missing       | zero session/user lookup             |
| Session digest not found                 | unauthenticated | Unknown       | one session lookup; zero user lookup |
| `Expires <= now`                         | unauthenticated | Expired       | one session lookup; zero user lookup |
| Active row, inactive owner               | unauthenticated | InactiveOwner | session then user lookup             |
| Session lookup infrastructure failure    | internal        | none          | no fallback                          |
| Orphan owner/owner lookup/decode failure | internal        | none          | no fallback                          |
| Valid unexpired session and active owner | success         | none          | exact principal                      |

Only the four typed unauthenticated outcomes may permit token fallback.
Adapters must use an explicit application helper and must not infer fallback
from the broad error reason.

`CurrentUser` uses this exact matrix: an unauthenticated Principal is generic
Unauthenticated with zero lookup; an active row succeeds; an inactive row is
generic Unauthenticated without a session-typed cause; and ErrNotFound,
lookup, or permission-decode failure is Internal. It must not disguise an
orphan/infrastructure failure as a missing credential.

### Password verification and login

- Empty username or password returns generic unauthenticated with zero lookup.
- A missing username runs the fixed dummy bcrypt comparison and returns the
  same generic result.
- A real lookup or permission-decode failure is Internal with its cause
  concealed from transports.
- For an existing row, bcrypt runs before the active-user rejection so bad
  password and inactive-owner results remain externally indistinguishable.
- `LoginReplacing` may perform bcrypt outside the transaction, but every login
  then unconditionally enters exactly one `Store.Transaction`, including a
  login without a presented session.
- Inside that transaction, reload the username and require the same user ID,
  active state, and constant-time equality with the already verified password
  hash. A missing/changed/inactive row is generic unauthenticated; an
  infrastructure failure is Internal.
- Generate a fresh random session secret, derive its CSRF value, take one UTC
  application-clock sample, and create a record with
  `Created == LastSeen == now` and `Expires == now + 12h`.
- If a prior session secret was presented, delete its digest only after final
  credential revalidation. Ignore only `ErrNotFound` for that attacker-selected
  prior value.
- Delete and create commit together. Any revalidation, delete, insert, or
  commit error returns no `BrowserSession` and leaves durable state unchanged.
- Authentication never refreshes `LastSeen`, expiry, the identifier, or CSRF.

The global PostgreSQL identity advisory transaction lock serializes login with
administrator reset/password writes. If login wins, the later reset deletes
the new session; if reset wins, the login's final password-hash revalidation
rejects the stale credential.

### CSRF verification and recovery

- `VerifyCSRF` uses the same typed session validation as authentication.
- After a valid session has resolved, empty CSRF or a digest mismatch is
  Forbidden, never Unauthenticated. Missing/unknown/expired session outcomes
  retain their session classification before CSRF is considered.
- Session/user infrastructure failures remain Internal.
- `CSRFForSession` accepts one nonempty raw session secret and performs one
  application transaction.
- Inside that transaction, reload and validate the session and active owner,
  derive the domain-separated value, and update `csrf_hash` only when it does
  not already equal the derived value's digest.
- The store receives only session and CSRF digests. A zero-row update maps to
  `ErrNotFound`; every other persistence error remains infrastructure failure.
- The exact Store-port addition is
  `UpdateSessionCSRF(context.Context, sessionHash, csrfHash []byte) error`; the
  PostgreSQL adapter updates only the existing `csrf_hash` column selected by
  `secret_hash` and never receives the raw derived value.
- If that update returns `ErrNotFound` after the preceding successful load,
  `CSRFForSession` maps the disappearance to typed Unknown; the REST bootstrap
  may then take its declared anonymous path. It must not return a derived value
  from the failed transaction or disguise another update failure as Unknown.
- Return the derived value only after the transaction commits.
- Concurrent calls for one session derive identical values and hashes, so
  response/write ordering cannot leave the browser with a losing token.
- A pre-I3 random stored hash is replaced on first successful authenticated
  bootstrap; until then its existing CSRF value remains valid.

### Transactional logout

- Empty input is typed Missing, not success.
- `Logout(ctx, sessionSecret, csrf)` always owns one `Store.Transaction`.
- Inside it, reload the exact session, enforce expiry and active owner, then
  revalidate the supplied CSRF digest against that same row and delete the same
  session digest.
- Unknown, expired, and inactive-owner states retain their typed outcome.
- A missing or mismatched CSRF value after valid-session resolution is
  Forbidden and leaves the row unchanged.
- Delete `ErrNotFound` is Unknown; every other store/user/delete/commit failure
  is Internal.
- Two concurrent logouts for one session yield exactly one success and one
  typed Unknown outcome, with no remaining row.

## REST contract

### Credential arbitration

Apply the following order in `BaselineMiddleware()` and `Middleware()`:

1. Parse session cookies without selecting the first duplicate.
2. More than one `sessionid` cookie fails closed with no token lookup: baseline
   middleware returns its generic 403 and extension middleware returns its
   generic 401.
3. Exactly one nonempty session cookie is authenticated first.
4. A valid active session is authoritative. Authorization is neither parsed
   nor looked up, even if malformed, duplicated, unsupported, or valid for a
   different user.
5. On a session-authenticated CSRF-protected method, any CSRF failure returns
   403 immediately and never falls through.
6. Missing, Unknown, Expired, and InactiveOwner may fall through to the
   existing transport-specific token parser.
7. A session infrastructure error returns 500 immediately with zero token
   lookup.
8. With no usable session, preserve I2 baseline Token behavior and the existing
   identity-extension Token behavior exactly.

Required simultaneous-credential rows:

| Session state                  | Authorization state             | Result                                |
| ------------------------------ | ------------------------------- | ------------------------------------- |
| Valid user A                   | Valid token for user B          | user A; zero token lookup/touch       |
| Valid                          | malformed/duplicate/unsupported | session success on a CSRF-safe method |
| Valid, protected method        | valid token, invalid CSRF       | 403; zero token lookup/touch          |
| Unknown/expired/inactive owner | valid token                     | token principal                       |
| Unknown/expired/inactive owner | malformed token                 | existing token-parser result          |
| Session infrastructure failure | any token                       | 500; zero token lookup/touch          |
| No session                     | valid token                     | existing I2 behavior                  |

Baseline missing/rejected credentials retain exact HTTP 403 JSON and no
`WWW-Authenticate`; the identity extension retains 401. A valid session plus
invalid CSRF is 403 on both.

### Separate method classifiers

- Session-CSRF-safe: `GET`, `HEAD`, `OPTIONS`, `TRACE`.
- Session-CSRF-protected: every other method, including `PROPFIND`.
- Token-read-safe: `GET`, `HEAD`, `OPTIONS` only.
- Token-write: every other method, including `TRACE` and unknown methods.

Never reuse one `unsafe` helper for both policies.

### Exact CSRF input

For login and every session-authenticated protected method:

- require exactly one nonempty `csrftoken` cookie;
- require exactly one nonempty `X-CSRFToken` header value;
- compare the literal values in constant time before stored-hash validation;
- reject missing, empty, duplicate, or unequal input with the generic 403;
- on login, reject before JSON binding, password lookup, throttle accounting,
  or session mutation; and
- on token-authenticated requests, ignore CSRF input because token requests do
  not use ambient browser credentials.

### CSRF bootstrap

`GET /api/auth/csrf/` remains public:

- No session cookie: emit a fresh 256-bit random pre-login value in one
  `csrftoken` cookie and the `csrf_token` response field; perform no store call.
- Valid session: call `CSRFForSession`, emit its derived value in the cookie and
  response; update the row only when healing a legacy/random hash.
- Unknown, expired, or inactive-owner session: behave as anonymous bootstrap
  without claiming that the session is valid.
- Session/store/user/commit infrastructure failure: 500 and no `Set-Cookie`.
- Duplicate `sessionid` cookies: fail closed with 403 and no replacement.

This fixes the current behavior that overwrites `csrftoken` while leaving an
active row bound to the old digest.

### Login and logout

- Login requires the exact pre-login CSRF pair and then calls the transactional
  application login. Success returns the existing session response and sets
  fresh `sessionid` plus session-derived `csrftoken` cookies.
- More than one `sessionid` cookie on login returns the generic 403 before CSRF
  evaluation, JSON binding, password lookup, throttle accounting, or store
  mutation and emits no `Set-Cookie`. One empty `sessionid` value is treated as
  no presented session; exactly one nonempty value is the rotation candidate.
- Login validates only the public pre-login double-submit CSRF pair. It does
  not authenticate the one presented `sessionid` or bind the pair to that
  session row; the value is only an attacker-controlled rotation candidate for
  `LoginReplacing` after password authentication succeeds.
- Login failure emits neither session nor CSRF replacement material.
- `/api/auth/logout/` uses dedicated session-only middleware. A token alone or
  an invalid-session-plus-valid-token request returns 401, performs no token
  lookup/touch, revokes nothing, and does not clear cookies.
- Duplicate `sessionid` cookies on logout return the same generic 401 before
  CSRF or application/store work and emit no tombstone.
- Valid-session logout ignores Authorization, requires exact CSRF, invokes the
  transactional application logout with the same CSRF candidate for in-
  transaction revalidation, and clears cookies only after commit.
- Successful logout remains 204 with no body.

### Cookie shape

| Property          | Session cookie                             | CSRF cookie                        |
| ----------------- | ------------------------------------------ | ---------------------------------- |
| Name              | `sessionid`                                | `csrftoken`                        |
| Path              | `/`                                        | `/`                                |
| Domain            | omitted/host-only                          | omitted/host-only                  |
| HttpOnly          | `true`                                     | `false`                            |
| SameSite          | `Lax`                                      | `Lax`                              |
| Secure            | runtime production setting                 | runtime production setting         |
| Max-Age on issue  | exactly 43,200 seconds                     | exactly 43,200 seconds             |
| Expires on issue  | exact application `BrowserSession.Expires` | optional; no wall-clock derivation |
| Response-body use | never                                      | bootstrap field only               |

Never calculate `Max-Age` with `time.Until`. Tombstones use the same
name/path/domain/security/SameSite/HttpOnly scope, an empty value, an emitted
`Max-Age=0`, and a past expiry.

zero-test runs cannot pass silently.
