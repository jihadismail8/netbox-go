## Required outcome

The pinned contract tree must contain one machine-readable matrix which:

- identifies the exact Compatibility Baseline SHA and active Capability
  Profile;
- covers every scenario declared by the profile;
- covers all 13 resources across `list`, `get`, `create`, `replace`, `update`,
  and `delete`, plus the two declared IPAddress assignment RPC actions;
- links one resource-contract row for each resource to its fields, choices,
  filters, ordering keys, relationships, and delete/side-effect metadata;
- covers every stable behavioral rule explicitly labeled in
  `docs/IMPLEMENTATION_PLAN.md`;
- resolves every row through an exact profile/resource reference set;
- records pinned upstream source and upstream-test references;
- records domain, application, PostgreSQL, baseline REST differential, gRPC
  parity, browser, identity-extension REST contract, and local-CLI security
  applicability independently from mutable proof state, then records exact
  references or an explicit pending/not-applicable reason through exhaustive
  row-to-applicability and row-to-proof mappings;
- independently pins the exact capability/dimension/reference test inventory,
  so changing an inventory and its consuming proof together cannot create
  coverage; verifies any future retained result through a versioned
  machine-readable attestation, a reachable exact Git revision, an owned
  raw-byte commitment to the result payload, an exact consumer-claim digest,
  and a Git-reconstructed complete tested-source manifest for every two-digest
  claim;
- records a current tier/evidence state without promoting any T1 resource or
  treating an identity extension as baseline-compatible; and
- classifies baseline credential-use and RBAC obligations as non-tier profile
  support, separate from the intentional identity-management extension.

Unresolved behavior must remain visible as `partial`, `pending`, or
`not_applicable`. The matrix must not call the existence of source or tests a
passing external boundary.

## Fixed matrix rules

1. Paths are repository-relative, cannot escape the repository, and must
   exist. Every reference also carries an exact anchor which must exist in the
   referenced file.
2. Scenario source IDs are the manifest IDs already declared by the profile.
3. Resource-operation source IDs are derived from the exact profile resource
   key and operation. The two extra IPAddress actions are derived from
   `extra_rpcs` rather than a handwritten exception list.
4. Stable plan rule IDs are semantic labels beginning with `plan.`. They do
   not contain line numbers or positional ordinals. The validator discovers
   the labels from the plan and requires exactly one matching rule row.
5. Each row has one stable ID, kind, source ID, primary capability, operation,
   reference set, verification set, and exactly one entry in `row_proofs`.
   The primary capability is the sole owner of the row's tier claim and the
   only profile tier which caps it. Multi-operation rules name every covered
   operation. Multi-capability rules name every dependency or observably
   affected capability and a reference set for each; those secondary entries
   expand proof authority but neither inherit nor block the owner's tier.
6. Reviewed row semantics pin every scenario, resource operation,
   resource-contract, and plan-rule binding: capability, operation, primary and
   related reference sets, affected capabilities, and covered operations.
   Reference sets link the profile/resource metadata, exact pinned source,
   upstream tests, and a capability-wide local test inventory. Cross-resource
   common-baseline, deferred-baseline, and identity-interface support use
   dedicated linked reference sets rather than an authority-free project
   placeholder. That inventory is context, not row proof. `proof_sets` own
   row-specific domain, application, PostgreSQL, baseline REST differential,
   gRPC parity, browser, extension REST, and local-CLI security state. The
   validator compares every reference set's classification, capability
   ownership, and exact dimension/status/reference inventory with an
   independently reviewed SHA-256; authority changes require explicit
   validator review, even when the consuming proof changes in the same patch.
7. Test-boundary state is one of `covered`, `partial`, `pending`, or
   `not_applicable`. `covered` and `partial` require live exact references;
   every other state requires a narrow reason. A proof set containing
   `partial` or `covered` state must be selected by exactly one row. Shared
   proof sets are permitted only while every dimension is explicitly
   `pending` or `not_applicable`. A separate reviewed applicability set marks
   each dimension `applicable` or `not_applicable`, and every row selects
   exactly one through `row_applicability`. Proof state cannot redefine that
   authority; reviewed N/A reasons must match exactly. Local coverage never
   implies a compatibility tier.
8. Baseline verification cannot exceed the resource tier in the active
   profile. T2 or higher additionally requires live retained evidence and the
   corresponding lower-tier boundary. Identity extension rows must use
   `not_applicable`, never a T tier. Every verification and assessment set must
   have a row consumer. Every retained verification records one immutable
   versioned `tested_digest` plus a full lowercase Git `tested_revision`
   reachable from current `HEAD`. The validator reconstructs the complete
   owned-source manifest from that commit with Git replacement objects and
   grafts disabled and requires its digest to equal the claim. A same-digest
   claim requires current owned source to equal the tested commit exactly.
   Every cited result contains exactly one matching single-line
   `netbox-go-evidence-v2` RFC 8259 JSON attestation for that verification set.
   Duplicate JSON members, forbidden whitespace, and unknown keys are
   rejected. Artifacts are hashed as raw bytes before fatal UTF-8 decoding;
   marker lines must be ASCII. Each evidence reference commits the SHA-256 of
   every exact non-marker byte, with no replacement decoding or newline
   normalization. The attestation binds its schema version, profile, exact
   baseline ID/SHA, verification set, classification, tier, optional extension
   axes, canonical proof dimensions, tested revision/digest, current
   `make source-digest` attestation digest, literal `pass` result, and a
   `claim_digest`. That claim digest covers the complete verification set and
   evidence references plus every sorted consumer's full row, assessment
   assignment/object, applicability assignment/object, and proof
   assignment/object. Rebinding any of them invalidates the marker.

   If source digests differ, the verification and attestation also bind one
   complete strict-JSON tested-source manifest by path and raw-byte SHA-256.
   It must match the replacement- and graft-disabled Git-reconstructed tested
   tree entry for entry; an asserted manifest or local Git metadata cannot
   invent history. `source-v2` file entries include normalized
   `100644`/`100755` mode, path, byte size, and content SHA-256. Symlinks use
   their literal relative target and must remain inside owned source, avoid
   link chains, and point to content independently present in the manifest.
   The validator requires identical tested/current path and kind sets, derives
   every mode/content change, and requires the ordered claim manifest to match
   every and only that diff with before/after modes, sizes, and hashes.
   Additions, deletions, kind changes, and symlink retargeting require rerunning
   evidence. Human review still decides whether each mechanically allowed file
   change is semantically claim-only. The attested dimensions must be
   applicable and covered across every consumer; a verification set includes
   only claimed tier/extension dimensions applicable to its own consumers,
   while resource/profile/extension aggregate gates enforce non-vacuity and
   complete cross-set closure. A retained extension report may cover a real
   subset while its axes remain `partial`; retention neither completes an axis
   nor awards a T tier. An extension axis becomes `complete` only when all of
   its applicable extension rows/dimensions and required support rows close.
   `make source-manifest` emits the tested manifest without changing the
   default `make source-digest` output; retain that JSON under `docs/evidence/`
   before making claim-only edits. Git reachability and these digests prove
   structural source/claim integrity, not that a command actually ran or that
   its result/environment is truthful; durable runner provenance and explicit
   human review remain mandatory external retention authority.

9. The validator rejects duplicate/extra/missing scenario, operation,
   resource-contract, and plan-rule rows; missing/extra row proof mappings;
   missing/extra row applicability mappings; shared live proof sets; a proof
   set shared across different applicability sets; proof/applicability drift
   or remapping from the reviewed 293-row authority; covered proof not
   declared by an affected capability's dimension-specific inventory; any
   coordinated drift of that reviewed inventory; drift of reviewed row
   semantics or pinned source/test authority; retained evidence outside a
   canonical, realpath-contained result artifact under `docs/evidence/`; a
   missing, malformed, duplicate-member, mismatched, stale-digest, or failed
   artifact attestation; uncommitted/tampered result payloads; incomplete,
   malformed, self-invented, or Git/digest-mismatched tested-source manifests;
   missing/unreachable tested revisions; invalid UTF-8 or non-ASCII markers;
   lossy payload hashing; stale consumer claim digests; omitted executable
   modes; escaping/chained/unowned symlinks; non-claim-only or
   incomplete derived diffs; added/deleted/type-changed source entries; unused
   verification/assessment sets; stale paths or anchors; invalid metadata selectors; missing proof or applicability
   dimensions or affected-capability references; classification mismatches;
   vacuous tier boundaries; and unsupported row-, resource-, profile-, or
   extension-level tier/evidence claims.
10. Matrix totals are derived from the authority files. Counts are diagnostic,
    never hard-coded substitutes for enumerating the actual keys.
