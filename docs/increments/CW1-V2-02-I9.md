Additional scalar rules:

- Site, RackType, and RackRole inputs stay inside the profile's positive
  numeric-ID envelope. Numeric strings, nested dictionaries, slug lookup, and
  generic relationship grammar are not promoted here.
- Name, facility ID, serial, asset tag, description, and comments use pinned
  DRF whitespace trimming and Unicode code-point limits where a limit exists.
  Only the declared blankable fields accept stored blank.
- Starting unit uses the inherited positive-small-integer storage envelope:
  values from 1 through 32,767 are accepted and 32,768 is rejected.
- Status, form factor, and airflow use the pinned choice values without
  whitespace trimming. Width is one of the four pinned integer choices.
- The pinned custom choice field converts explicit REST `null` airflow to a
  present blank value because airflow permits blank but not null. Omitted
  airflow on create remains database null. Protobuf has no identical JSON-null
  grammar and preserves the nearest representable explicit blank intent.
- `facility_id` and `rack_type` are the only fields in this slice with explicit
  serializer defaults on full replacement. PUT omission resets each to null;
  every other optional PUT omission preserves current state.
- A non-null RackType owns `form_factor`, `width`, `u_height`, `starting_unit`,
  and `desc_units` on every direct Rack save. Its snapshot overrides conflicting
  submitted values after create, PUT, or PATCH. Clearing RackType stops future
  copying and preserves the existing physical snapshot unless the same request
  supplies direct physical replacements.
- I9 direct-save fixtures contain no Devices, keep Location null, and keep the
  Site stable. They therefore do not exercise mounted-device protection,
  Location/Site validation, Device site propagation, RackType-update
  propagation, placement, or occupancy.
- Asset-tag uniqueness and Location-scoped name/facility uniqueness remain
  open. Fixtures use null or unique asset tags and make no uniqueness claim.
- Combined violations return once in deterministic owned-field order without
  discarding valid sibling-field intent.
- POST retains add permission and PUT/PATCH retain change permission; I9 uses
  authorized principals and does not expand the RBAC matrix.
- Every mutation uses one application-owned PostgreSQL transaction.
  Relationship resolution, authorization, normalization, validation,
  persistence, and exactly one typed Rack object change share that transaction.
- Validation rejection leaves state, timestamp, repository mutation count,
  and object-change count unchanged. Repository or recorder failure rolls all
  durable state and object changes back.

Generic coercion, malformed UTF-8, byte-exact framework diagnostics, empty
PATCH, alternate relationship input, and diagnostic multiplicity remain out
of scope. PATCH omission tests include a concrete sibling field.
