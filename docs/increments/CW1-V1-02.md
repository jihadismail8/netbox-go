## Outcome

Make the shared Go token authenticator and its PostgreSQL conditional update
match the pinned baseline wherever the baseline has an equivalent state, while
preserving the project's explicit soft-revocation extension:

1. Missing and unknown secret material is rejected without a token-row write.
2. A token whose persisted owner cannot be loaded is an internal storage
   failure, not an unknown credential, and performs no token-row write.
3. A soft-revoked row is treated like a deleted baseline token and rejected
   without a post-revocation `last_used` write.
4. A recognized, non-revoked row is eligible for a touch only when `last_used`
   is absent or the elapsed interval is strictly greater than 60 seconds.
5. An eligible touch happens before expiration, inactive-user, source-IP, and
   write-disabled rejection.
6. A touch failure is not ignored. It becomes the stable typed internal result
   and authentication stops.
7. The PostgreSQL predicate independently enforces the same strict boundary so
   concurrent callers cannot turn an exactly-60-second request into a write.

This outcome supplies the stable lowest-layer truth required by later
transport rows. It does not complete `CW1-V1-02`.

## Fixed application semantics

### Lookup and recognition

- An empty secret returns `unauthenticated` before hashing or store lookup.
- A store lookup that returns `ErrNotFound` returns `unauthenticated` and never
  calls `TouchToken`.
- Any other lookup, storage, decode, or owner-load failure returns typed
  `internal`, preserves its cause for server-side inspection, and never calls
  `TouchToken`. Infrastructure failures must not be disguised as an unknown
  credential.
- This slice does not change the public error message. Tests assert the typed
  reason and durable effect, not secret-bearing text.
- Once the store returns a token row and its owner, the row is recognized.
- A recognized row with `RevokedAt != nil` returns `unauthenticated` before
  `TouchToken`. This is the exact local analogue of a baseline-deleted row.

### Strict touch boundary

Let `now` be the single UTC value returned by the injected clock for the
authentication attempt.

- `LastUsed == nil`: call `TouchToken(id, now)` once.
- `now - LastUsed < 60s`: do not call it.
- `now - LastUsed == 60s`: do not call it.
- `now - LastUsed > 60s`: call it once.
- A future `LastUsed` value is not eligible for a touch.
- Do not read the clock a second time inside the application operation.

The store must use:

```text
id matches
AND revoked_at IS NULL
AND (last_used IS NULL OR last_used < now - 60 seconds)
```

It must not use `<=`. The application guard controls ordinary write load; the
SQL guard is still required for concurrent/stale callers. The revocation
predicate prevents a caller which loaded immediately before revocation from
performing a post-revocation touch.

Two coordinated callers which both observed an eligible stale value must yield
exactly one durable `last_used` update. The PostgreSQL proof must count actual
updates with an increment-owned trigger/audit row; checking only the final
timestamp is insufficient.

### Ordering and failure

After recognition and revocation rejection, the operation order is fixed:

1. Conditionally touch.
2. If the touch returns an error, return typed `internal` immediately.
3. Reject an expiry where `expires <= now` as `unauthenticated`.
4. Reject an inactive owner as `unauthenticated`.
5. If restrictions exist, reject an address outside every allowed prefix as
   `unauthenticated`.
6. For an unsafe operation, reject `WriteEnabled == false` as `forbidden`.
7. Return the loaded active user.

An eligible expired, inactive-owner, IP-denied, or write-disabled row is
therefore touched before its eventual rejection, matching the pinned
authentication/permission ordering. A revoked row is the deliberate exception
because the baseline row no longer exists after revocation.

IP validation precedes unsafe-method write permission because the pinned
authenticator finishes its source restriction before DRF invokes
`TokenPermissions`. A token that is both IP-disallowed and write-disabled must
therefore be `unauthenticated`, not `forbidden`.
