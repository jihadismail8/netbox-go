## Required observable contract

### Create, replace, and update

| Field         | POST omitted       | PUT omitted                | PATCH omitted | Explicit `null`          | Explicit blank/false/concrete                         |
| ------------- | ------------------ | -------------------------- | ------------- | ------------------------ | ----------------------------------------------------- |
| `parent`      | root / `null`      | reset to root / `null`     | preserve      | root / clear             | positive numeric ID only; zero/missing ID rejected    |
| `name`        | required error     | required error             | preserve      | reject: may not be null  | blank rejected; trim; maximum 100 code points         |
| `slug`        | required error     | required error             | preserve      | reject: may not be null  | blank rejected; trim; ASCII slug; maximum 100         |
| `color`       | default `9e9e9e`   | preserve                   | preserve      | reject: may not be null  | blank rejected; trim; six lowercase hexadecimal chars |
| `vm_role`     | default `true`     | preserve                   | preserve      | reject: may not be null  | explicit `false` persists                             |
| `description` | default `""`      | preserve                   | preserve      | reject: may not be null  | blank clears; trim; maximum 200 code points           |
| `comments`    | default `""`      | preserve                   | preserve      | reject: may not be null  | blank clears; trim; no new maximum claim              |

Additional scalar rules:

- slug uses the pinned ASCII `^[-a-zA-Z0-9_]+$` grammar and is not generated;
- color accepts exactly six lowercase hexadecimal characters after trimming;
- relationship input stays inside the profile's positive numeric-ID envelope;
  upstream dictionary/string lookup forms are not promoted by this child;
- combined violations are returned once in deterministic field order without
  discarding valid sibling-field state;
- POST retains add permission and PUT/PATCH retain change permission; this
  increment uses authorized principals and does not expand the RBAC matrix;
- every mutation uses one application-owned PostgreSQL transaction;
  relationship resolution, authorization, validation, persistence, hierarchy
  projection already owned by the existing service, and object-change
  recording share that transaction;
- validation rejection leaves DeviceRole state, timestamps, hierarchy state,
  repository mutation counts, and object-change count unchanged;
- a repository or first object-change-recorder failure after an attempted
  write rolls all durable DeviceRole state and object changes back; and
- successful POST/PUT/PATCH writes the intended state and exactly one typed
  DeviceRole object change.

Generic numeric/string coercion, malformed UTF-8 behavior, exact framework
diagnostic multiplicity, empty PATCH, relationship-dictionary inputs, and
byte-exact errors beyond the field-scoped matrix are not claimed. PATCH
omission tests include a concrete sibling field.

### Contract metadata and generated OpenAPI

DeviceRole metadata must add:

```json
"field_contracts": {
  "response": {
    "nullable_fields": ["parent", "created", "last_updated"]
  },
  "create": {
    "required_fields": ["name", "slug"],
    "nullable_fields": ["parent"],
    "blank_fields": ["description", "comments"]
  },
  "replace": {
    "required_fields": ["name", "slug"],
    "nullable_fields": ["parent"],
    "blank_fields": ["description", "comments"]
  },
  "update": {
    "required_fields": [],
    "nullable_fields": ["parent"],
    "blank_fields": ["description", "comments"]
  }
}
```

- The profile validator makes DeviceRole operation metadata mandatory and
  rejects missing operations, undeclared/duplicate fields, invalid subsets,
  and response/write conflation.
- Generated OpenAPI replaces `DeviceRoleWrite` with `DeviceRoleCreate`,
  `DeviceRoleReplace`, and `DeviceRoleUpdate`; POST/PUT/PATCH reference the
  matching schema.
- Create and replace require only name and slug; update requires no fields.
- Request parent is a nullable `int64`; response parent is a nullable
  `ObjectReference`.
- Name, slug, color, description, comments, display, URL, booleans, IDs, and
  counters are non-null in the response. Only parent, created, and
  last_updated are nullable.
- Generated files change only through owned metadata/generator inputs.

### REST, gRPC, traceability, and Vue

- REST preserves omitted/null/blank/zero/false/concrete states through the
  typed decoder and central error mapper. A production handler change is
  allowed only if a red DeviceRole decoder regression proves a gap.
- Existing optional protobuf scalars preserve omission and concrete false.
  For PATCH, a FieldMask path with an absent optional value means explicit-null
  intent and reaches the same application validation; parent maps that intent
  to clear/root. Unknown paths fail closed.
- Optional proto messages cannot independently encode omitted versus explicit
  null parent on POST/PUT. No protobuf redesign or regeneration is authorized,
  exact REST stays authoritative, and no T3 claim is made.
- Traceability adds only an unresolved
  `unresolved-device-role-scalar-presence` assessment and points only the
  DeviceRole resource-contract and create/replace/update operation rows to it.
  List/get/delete, hierarchy/uniqueness/delete rules, applicability,
  verification, consumer, and tier rows do not change.
- Vue types DeviceRole response timestamps as `string | null`, preserves
  create defaults, and keeps name/slug required.
- Vue serializes only form-owned fields, preserves null/false/blank/concrete,
  converts parent selection to its ID, and keeps a private normalized edit
  baseline so unchanged edits emit no scalar.
- Vue field-scoped backend validation reaches the matching control; Vue does
  not own authorization, relationship validity, or hierarchy validity.
