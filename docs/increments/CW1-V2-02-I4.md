## Required observable contract

### Create, replace, and update

| Field         | POST omitted     | PUT omitted    | PATCH omitted | Explicit `null`         | Explicit `""`            |
| ------------- | ---------------- | -------------- | ------------- | ----------------------- | ------------------------ |
| `name`        | required error   | required error | preserve      | reject: may not be null | reject: may not be blank |
| `slug`        | required error   | required error | preserve      | reject: may not be null | reject: may not be blank |
| `color`       | default `9e9e9e` | preserve       | preserve      | reject: may not be null | reject: may not be blank |
| `description` | default `""`     | preserve       | preserve      | reject: may not be null | clear to `""`            |

Additional scalar rules:

- all four values are trimmed before semantic validation;
- name and slug are required nonblank strings limited to 100 Unicode code
  points; description is blankable and limited to 200 Unicode code points;
- slug uses the pinned ASCII `^[-a-zA-Z0-9_]+$` grammar and is never generated
  by the REST API;
- nonblank color is trimmed and must match exactly six lowercase ASCII
  hexadecimal characters under `^[0-9a-f]{6}$`; uppercase, a leading `#`,
  non-hexadecimal characters, and every other length are rejected, with the
  custom `Enter a valid hexadecimal RGB color code.` diagnostic pinned for
  grammar failures while overlapping generic max-length diagnostic
  multiplicity remains outside this byte-exact claim;
- blank or whitespace-only color is rejected with
  `This field may not be blank.`; blank or whitespace-only description clears
  to the empty string;
- combined field violations are returned once in deterministic name, slug,
  color, description order without discarding valid sibling-field state;
- existing authorization remains unchanged: POST uses add permission and
  PUT/PATCH use change permission; this increment exercises an authorized
  principal and does not expand the RBAC matrix;
- each public POST/PUT/PATCH uses exactly one application-owned PostgreSQL
  transaction; PUT/PATCH load the target through `GetForUpdate`, and
  in-transaction candidate/object authorization, command and domain
  validation, persistence, and typed object-change recording share that
  transaction;
- every validation-rejected POST/PUT/PATCH leaves the RackRole row, `created`,
  `last_updated`, `rack_count`, repository create/update call count, and
  object-change count unchanged;
- a persistence or object-change-recorder failure may follow an attempted
  repository write, but it rolls back the durable RackRole row, `created`,
  `last_updated`, `rack_count`, and object-change count to their exact prior
  state; and
- each successful POST/PUT/PATCH writes the intended state and exactly one
  object change in that transaction.

Generic DRF numeric-to-string coercion, malformed UTF-8 parser behavior, and
byte-exact generic character-field diagnostics are not promoted by this
bounded presence increment. Tests pin the field-scoped public diagnostics
without claiming a retained T2 boundary. PATCH-omission tests must include a
concrete sibling so this packet does not decide empty-PATCH behavior.

### Contract metadata and generated OpenAPI

RackRole resource metadata must add this operation-specific authority:

```json
"field_contracts": {
  "response": {
    "nullable_fields": ["created", "last_updated"]
  },
  "create": {
    "required_fields": ["name", "slug"],
    "nullable_fields": [],
    "blank_fields": ["description"]
  },
  "replace": {
    "required_fields": ["name", "slug"],
    "nullable_fields": [],
    "blank_fields": ["description"]
  },
  "update": {
    "required_fields": [],
    "nullable_fields": [],
    "blank_fields": ["description"]
  }
}
```

- The profile validator makes RackRole operation metadata mandatory and
  rejects missing operations, undeclared or duplicate fields, invalid
  required/null/blank subsets, and response/write conflation.
- Generated OpenAPI uses `RackRoleCreate`, `RackRoleReplace`, and
  `RackRoleUpdate`; POST, PUT, and PATCH reference their corresponding schema,
  and the stale shared nullable `RackRoleWrite` schema disappears.
- Create and replace require name and slug; update requires none. All four
  write scalars are non-nullable and only description is blankable.
- The RackRole response advertises nullable baseline timestamps but non-null
  name, slug, color, description, display, URL, ID, and declared rack count.
- Color regex/length remain pinned in domain/application/transport tests for
  this increment. Expanding the resource-metadata schema or generic generator
  to carry regex/length is outside this reviewed packet.
- Generated files are produced only from owned metadata/generator inputs and
  are never edited by hand.

### REST, gRPC, traceability, and Vue

- REST preserves omitted, null, blank, and concrete field states through the
  existing typed decoder and maps field failures through the central error
  path.
- Existing optional protobuf scalars preserve omission and blank. For PATCH,
  a FieldMask path with the scalar absent represents explicit null intent and
  reaches the same field-specific application validation. Optional proto
  scalars cannot separately express POST/PUT null; this bounded increment does
  not redesign or regenerate protobufs.
- Unsupported gRPC mask paths remain fail-closed.
- Traceability may add only an unresolved
  `unresolved-rack-role-scalar-presence` assessment and point
  `resource.dcim.rack-role.contract`, `operation.dcim.rack-role.create`,
  `operation.dcim.rack-role.replace`, and `operation.dcim.rack-role.update` to
  it. List/get/delete, uniqueness, protected deletion, proof sets,
  verification sets, consumer mappings, tiers, and row count do not change.
- Vue models RackRole response timestamps as `string | null`, keeps name and
  slug required, keeps color and description optional, and preloads color with
  `9e9e9e` for create.
- Vue create serialization preserves omitted, blank, and concrete values.
  Edit hydration retains a private original scalar snapshot so an unchanged
  edit emits no RackRole scalar, clearing description emits `""`, and changing
  name, slug, or color emits only that field.
- Field-scoped REST validation reaches the matching form control. Vue does not
  own authorization or a second business-error taxonomy.
