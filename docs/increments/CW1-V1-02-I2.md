## Outcome

Deliver one coherent token-transport slice:

1. The identity application service returns transport-neutral typed causes for
   missing, unknown, revoked, expired, inactive-owner, unavailable-source, and
   denied-source token failures without changing I1 ordering or effects.
2. Baseline REST middleware implements the pinned DRF single-header `Token`
   grammar and exact declared failure details using HTTP 403 without
   `WWW-Authenticate`.
3. Unary gRPC middleware implements the documented strict `Bearer` grammar,
   uses generated full-method constants for its read allowlist, and treats all
   unknown methods as writes.
4. REST and gRPC continue through the same `AuthenticateToken` operation and
   prove matching principal, typed cause, lookup/touch effect, and handler
   containment wherever applicable.

This outcome closes neither browser-session rows nor the parent goal.

## Fixed application contract

Add a transport-neutral application type with this semantic surface:

```text
TokenCredentialFailureKind

TokenCredentialFailureMissing
TokenCredentialFailureUnknown
TokenCredentialFailureRevoked
TokenCredentialFailureExpired
TokenCredentialFailureInactiveOwner
TokenCredentialFailureSourceUnavailable
TokenCredentialFailureSourceDenied

TokenCredentialFailure {
    Kind
    SourceIP
}
```

Requirements:

- The failure is discoverable through `errors.As`; a helper may return a
  defensive value rather than a mutable embedded pointer.
- `SourceIP` is nonempty only for `SourceDenied` and contains the canonical
  parsed direct-peer address without a port.
- Each typed failure is the cause of an outer `shared.Error` whose reason is
  `unauthenticated` and whose public application message remains generic.
- The REST baseline adapter may inspect the typed cause. gRPC must keep the
  generic application message.
- Lookup/touch infrastructure failures stay `internal` and never receive a
  credential-failure kind.
- Write-disabled stays `forbidden` and never receives a credential-failure
  kind.

| State                                             | Shared reason     | Typed kind          | Touch behavior       |
| ------------------------------------------------- | ----------------- | ------------------- | -------------------- |
| Empty secret                                      | `unauthenticated` | `Missing`           | zero                 |
| Store not found                                   | `unauthenticated` | `Unknown`           | zero                 |
| Soft-revoked row                                  | `unauthenticated` | `Revoked`           | zero                 |
| Expired recognized row                            | `unauthenticated` | `Expired`           | preserve I1 ordering |
| Inactive owner                                    | `unauthenticated` | `InactiveOwner`     | preserve I1 ordering |
| Restricted token, missing/malformed direct peer   | `unauthenticated` | `SourceUnavailable` | preserve I1 ordering |
| Restricted token, parsed but denied direct peer   | `unauthenticated` | `SourceDenied`      | preserve I1 ordering |
| Write-disabled token used for an unsafe operation | `forbidden`       | none                | preserve I1 ordering |
| Lookup/touch infrastructure failure               | `internal`        | none                | preserve I1 ordering |
| Valid token                                       | success           | none                | preserve I1 ordering |

### Direct-peer rules

- Inspect only the adapter-supplied peer string.
- Accept bare IPv4, IPv4 host-port, bare IPv6, and bracketed IPv6 host-port.
- Parse and canonicalize with `net/netip`.
- Parse the peer only when the token has source restrictions.
- Treat an absent or malformed peer as `SourceUnavailable`.
- Treat a parsed peer outside every valid prefix as `SourceDenied`.
- Invalid persisted prefixes remain fail-closed; this increment does not add
  persistence repair.
- Do not inspect `X-Real-IP`, `X-Forwarded-For`, `Forwarded`, or proxy config.

## Exact baseline REST contract

These rules apply only to `BaselineMiddleware()`.

### Header grammar

- Inspect `c.Request.Header.Values("Authorization")`, not `Header.Get`.
- Zero values means no credential.
- More than one field value fails closed as no credential and performs zero
  store lookups.
- For exactly one value, split only on Python bytes-whitespace bytes `0x09`
  through `0x0d` and `0x20`. Do not use Unicode-aware field splitting.
- Compare `Token` with ASCII-only case folding.
- Leading, trailing, and repeated permitted ASCII separators are accepted.
- A `Token` field without a second field is the no-credentials header error.
- More than two fields is the spaces header error.
- Check UTF-8 validity only on the single credential field after field-count
  validation.
- Unsupported schemes, a value without the Token scheme, empty input, and
  whitespace-only input behave as no credential.
- Treat the parsed credential as opaque and unchanged.
- Every rejected header shape performs zero store lookups.
- Do not construct CR/LF-bearing HTTP requests that Go correctly rejects; a
  pure byte-level helper test may cover parser-only byte cases.

### Baseline response matrix

Every rejection uses a one-field JSON `detail` object, invokes no protected
handler, and omits `WWW-Authenticate`.

| Case                                             |       HTTP | Exact `detail`                                                                                                                                 |
| ------------------------------------------------ | ---------: | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Absent/empty/ASCII-whitespace-only               |        403 | `Authentication credentials were not provided.`                                                                                                |
| Unsupported scheme, including `Bearer`           |        403 | `Authentication credentials were not provided.`                                                                                                |
| Duplicate header values                          |        403 | `Authentication credentials were not provided.`                                                                                                |
| `Token` without a credential                     |        403 | `Invalid token header. No credentials provided.`                                                                                               |
| More than two fields                             |        403 | `Invalid token header. Token string should not contain spaces.`                                                                                |
| Invalid UTF-8 credential                         |        403 | `Invalid token header. Token string should not contain invalid characters.`                                                                    |
| Unknown token                                    |        403 | `Invalid token`                                                                                                                                |
| Soft-revoked token                               |        403 | `Invalid token`                                                                                                                                |
| Expired token                                    |        403 | `Token expired`                                                                                                                                |
| Inactive owner                                   |        403 | `User inactive`                                                                                                                                |
| Restricted token without a parseable direct peer |        403 | `Client IP address could not be determined for validation. Check that the HTTP server is correctly configured to pass the required header(s).` |
| Denied source                                    |        403 | `Source IP 198.51.100.1 is not permitted to authenticate using this token.`                                                                    |
| Write-disabled unsafe request                    |        403 | `You do not have permission to perform this action.`                                                                                           |
| Infrastructure failure                           |        500 | `An internal error occurred.`                                                                                                                  |
| Valid token                                      | downstream | protected handler receives the principal                                                                                                       |

`GET`, `HEAD`, and `OPTIONS` are safe. `POST`, `PUT`, `PATCH`, `DELETE`, and
representative extension methods such as `PROPFIND` are unsafe.

The Go-owned identity extension retains its existing 401 boundary and current
parser behavior through `Middleware()`. A request containing both a session
cookie and an Authorization field is not a proven precedence row in I2.

## Exact unary gRPC contract

### Bearer metadata grammar

- Read exactly one lowercase `authorization` metadata value.
- Compare `Bearer` with ASCII-only case folding.
- Require one or more ASCII spaces (`1*SP`) between scheme and credential.
- Require one nonempty opaque credential containing only visible ASCII bytes
  `0x21` through `0x7e`.
- Reject leading or trailing whitespace, HTAB separators, control bytes,
  embedded spaces, extra fields, empty credentials, unsupported schemes, and
  duplicate metadata values.
- Reject malformed shapes before application/store lookup.
- Never expose the metadata value in a status message or diagnostic.

### Public/read/write classification

- Only `grpc_health_v1.Health_Check_FullMethodName` bypasses unary
  authentication.
- Health `Watch` and both reflection services are streaming and explicitly
  deferred.
- Protected read methods are an explicit switch over generated constants:
  - Identity: `GetCurrentUser`, `ListAPITokens`.
  - DCIM: `List`/`Get` for Sites, Manufacturers, RackRoles, RackTypes, Racks,
    DeviceRoles, DeviceTypes, InterfaceTemplates, Devices, and Interfaces.
  - IPAM: `List`/`Get` for VRFs, Prefixes, and IPAddresses.
- Every other canonical method and every unknown method defaults to a write.
- Names such as `/Getaway` and `/ListSomething` must not be inferred as reads.

Descriptor-backed tests must prove:

| Service  | Reads | Writes | Protected unary total |
| -------- | ----: | -----: | --------------------: |
| DCIM     |    20 |     40 |                    60 |
| IPAM     |     6 |     14 |                    20 |
| Identity |     2 |      3 |                     5 |
| Total    |    28 |     57 |                    85 |

### gRPC result matrix

| State                                           | Result             |
| ----------------------------------------------- | ------------------ |
| Missing/malformed/duplicate metadata            | `Unauthenticated`  |
| Unknown/revoked/expired/inactive/source failure | `Unauthenticated`  |
| Valid read-only token on allowlisted read       | success            |
| Read-only token on mutation or unknown method   | `PermissionDenied` |
| Lookup/touch infrastructure failure             | `Internal`         |
| Valid write-enabled token                       | success            |

All unauthenticated gRPC cases retain the generic safe application message.
REST-only state detail must not leak into gRPC.

## Cross-transport parity matrix

The shared parity test covers valid principal, unknown, revoked, expired,
inactive owner, unavailable source, denied source, write-disabled, and
infrastructure-failure rows. For each applicable row assert:

- the same application credential kind;
- matching lookup/touch counts and ordering;
- matching handler invocation or containment;
- the same effective principal on success;
- exact REST representation and the corresponding stable gRPC code;
- no forbidden durable effect; and
- no credential material in subtest names, diagnostics, or retained output.

Representation differs intentionally: exact pinned REST details are a
baseline contract, while gRPC keeps generic safe messages and semantic codes.
