These sources decide the browser-session semantic: the browser which changes
its password keeps an authenticated session under a rotated identifier, while
prior identifiers and sibling sessions stop authenticating. The Go identity
store has no public arbitrary-session-data or session-list surface, so eagerly
deleting all old Go session rows and inserting one replacement is observably
equivalent for the declared profile to Django's current-session rotation plus
lazy rejection of sibling auth hashes.

The Go route `POST /api/auth/password/change/` and gRPC `ChangePassword` RPC are
classified extension interfaces, not NetBox's HTML redirect response. Their
existing 204 and empty-protobuf shapes stay unchanged. Token-origin password
change has no direct Django browser equivalent; its outcome is fixed by the
accepted session-invalidation rule and the explicit absence of a cookie-shaped
gRPC equivalent.

### Fixed I4 extension policy

- A browser-session-origin REST password change rotates the originating
  browser into exactly one fresh I3-shaped session, revokes every old session
  for that user including the originating and sibling rows, and returns fresh
  `sessionid` and `csrftoken` cookies after commit.
- A REST Token-origin password change revokes every browser session for that
  user and returns no browser credential or cookie mutation.
- A bearer-gRPC password change has Token provenance, revokes every browser
  session, and returns the existing empty response.
- API tokens are not password sessions. Password change neither revokes nor
  rotates them; the credential which authenticated a token-origin request
  remains governed by the independent token lifecycle.
- A valid session remains authoritative over Authorization and therefore uses
  browser provenance. Only I3's permitted invalid-session fallthrough can
  result in Token provenance.
- A Token-origin request with an unknown, expired, or inactive-owner ambient
  session cookie emits no tombstone and no replacement cookie.
- A fresh browser replacement uses the accepted I3 fixed, non-sliding 12-hour
  lifetime. This packet does not reopen I3's session-lifetime policy.

No new owner decision remains for that bounded policy. Any attempt to settle
NetBox password validators, Django/PBKDF2 compatibility, bcrypt input limits,
hash versioning, rehash-on-login, imported hashes, administrator recovery, or
CLI policy is a separate hard-to-reverse security/data decision and a stop
condition here.

## Outcome

Deliver one coherent password-change vertical slice:

1. The application receives a sealed, transport-neutral password-change
   credential provenance value and never infers it from a Principal or ambient
   input.
2. Current-password mismatch stays a stable field validation failure, while a
   malformed verifier and infrastructure failures remain Internal.
3. Every preverified change revalidates user, password-hash state, and—when
   browser-origin—session owner, expiry, and CSRF inside one application-owned
   transaction.
4. Browser origin updates the password, deletes all old sessions, creates one
   fresh replacement, and returns replacement material only after commit.
5. REST Token and gRPC bearer origin update the password and delete all browser
   sessions without creating or returning a browser replacement.
6. REST preserves 204 and emits exactly the cookie behavior declared below;
   gRPC preserves its empty response and has semantic state/error parity.
7. PostgreSQL proof covers real update/delete/create rollback and a
   deterministically coordinated concurrent-change race under the existing
   advisory transaction lock.

I4 does not complete the parent credential matrix. Throttles, trusted-proxy
source resolution, password-policy/hash lifecycle, gRPC streaming,
Origin/HTTPS-Referer/masked-CSRF policy, aggregate all-transport evidence, and
browser T4 remain open.

Requirements:

- Each exported application type above is a sealed interface. Its unexported
  marker prevents transport packages from implementing it.
- Each constructor returns a non-nil pointer to one private concrete type for
  that interface. Browser and Token credential constructors use the same
  private concrete credential type, so `%T` cannot reveal the winning kind.
- The private credential kind and all contained fields remain inaccessible;
  callers use only the two constructors. A nil interface, typed-nil private
  pointer, or package-internal unknown/inconsistent kind fails closed.
- A constructor-created browser credential remains valid provenance when its
  session secret is empty; it enters the transaction and receives I3's typed
  session Missing result. It is not the nil/unknown-provenance case.
- Token provenance carries no reusable token secret and cannot produce a
  browser result.
- Browser provenance carries the exact session secret and CSRF candidate only
  for request-lifetime in-transaction revalidation. It is never persisted,
  returned as input, or deliberately logged.
- The private concrete input contains the current password, new password, and
  credential. Callers use `NewPasswordChangeInput`; a transport cannot
  construct a raw-map, struct literal, or tagged DTO at the application
  boundary.
- The Service type-checks the input interface before reading it. A nil,
  typed-nil, or package-internal unknown input implementation is an Internal
  application-wiring failure with a nil result and zero lookup, transaction, or
  write; it must never panic.
- The private concrete result contains the optional browser session. REST uses
  only the typed `BrowserSession() (domain.BrowserSession, bool)` accessor after
  success; Token origin reports `false` and the zero session value, while every
  failure returns a nil result interface.
- Credential, input, and result `String`, `GoString`, and `Format` methods return
  fixed type-specific redacted literals containing no kind, presence, password,
  secret, CSRF, hash, user, or other caller value. `Format` ignores every verb,
  flag, width, and precision and never delegates to recursive field formatting.
- Go `fmt` bypasses `Formatter` for `%p` and `%T`; the pointer-only private
  representation makes those cases address-only and type-only. `%T` is the same
  private concrete credential type for both credential kinds. No secret-bearing
  concrete value is ever stored directly in an exported value type.
- Credential, input, and result `MarshalJSON` methods always return nil bytes
  plus a generic non-secret error. Accidental `encoding/json` serialization
  must fail rather than emit `{}` or an exported nested session.
- The private concrete types have no JSON, protobuf, GORM, or HTTP tags,
  implement the safe fixed-redaction `fmt.Formatter` above, and implement no
  value-revealing text, binary, marshal, or logging method.
- `domain.Principal` remains unchanged and credential-free.
- `BrowserSession()` reports present only after a committed browser-origin
  change. Token-origin success reports absent; failure returns a nil result.
- Existing direct application callers migrate explicitly to one constructor;
  no compatibility overload accepting two raw password strings is retained.

### Pre-transaction verification

The expensive bcrypt comparison and next-hash generation may happen before
the database transaction, but they are speculative and cannot authorize a
commit by themselves:

1. Type-check the input interface. Reject nil, typed-nil, or package-internal
   unknown input as Internal before reading any private field.
2. Reject an unauthenticated Principal or a nil, typed-nil, unknown, or
   inconsistent provenance value before lookup.
3. Load the user and stored current hash by `principal.ID`.
4. Map `ErrNotFound` and every infrastructure/decode error to Internal, matching
   I3's orphan handling for an already authenticated Principal.
5. Run bcrypt comparison before deciding returned-ID, activity, or mismatch
   outcomes. A malformed or unsupported verifier is Internal immediately.
6. After verifier work, map an impossible returned user ID different from the
   Principal ID to Internal.
7. Reject an inactive returned user as Unauthenticated regardless of whether
   the supplied password also mismatched. This preserves I3's inactive-user
   concealment; malformed verifier still wins as Internal.
8. For an active, correctly identified user, map only
   `bcrypt.ErrMismatchedHashAndPassword` to the existing `current_password`
   validation failure.
9. Run the unchanged `HashPassword` path over the input's private new-password
   value. Do not alter its policy or outcome in I4.
10. If those checks succeed, enter exactly one `Store.Transaction`; never
    persist or return a result before it commits.

Wrong current password and unchanged new-password-policy rejection perform
zero transactions and zero mutation. Every request which passes those
speculative checks performs exactly one transaction even if final state has
changed concurrently.

### In-transaction order

Inside the existing globally serialized identity transaction, perform this
order exactly:

1. Take one UTC application-clock sample named conceptually `now`.
2. Reload the user and current password hash by the same Principal ID.
3. Map transactional `ErrNotFound`, decode/infrastructure error, or an
   impossible different returned ID to Internal; authenticated-user
   disappearance is an orphan/infrastructure condition, not a missing
   credential.
4. Compute constant-time equality between the reloaded hash and the exact hash
   verified before the transaction, but do not branch on it yet.
5. Require the reloaded user to remain active; inactivity is Unauthenticated
   even when the hash also changed.
6. For the still-active user, map a false hash comparison to the stable
   `current_password` validation failure.
7. For browser provenance only, digest and load the exact originating session;
   require that it exists, has `Expires > now`, belongs to the same user, and
   has a constant-time CSRF-digest match for the exact candidate.
8. For browser provenance only, generate a 256-bit random raw-URL session
   secret, derive its I3 CSRF value, and transactionally probe the candidate
   digest before any mutation. A collision with an originating or sibling
   session owned by this user is Internal and stops before the password update;
   a probe infrastructure failure is Internal. A collision owned by another
   user deliberately continues to the unique-insert boundary so that the real
   update/delete/insert rollback path remains proved. Construct the replacement
   record with `Created == LastSeen == now` and `Expires == now + 12h`.
9. Update the password hash and user `updated` value using `now`.
10. Delete every browser session row for the user.
11. For browser provenance only, insert exactly the one replacement record.
12. Return from the transaction callback and wait for commit.
13. Expose the replacement result only after commit succeeds.

User/hash revalidation deliberately precedes session revalidation. Therefore,
when two requests both preverify the same old password and the first commits,
the serialized loser deterministically receives the stable
`current_password` failure instead of a race-dependent Unknown-session result.

The transaction must use a fixed-time helper for session expiry rather than
calling the current clock-sampling session helper and then sampling again.
Existing non-password session methods need not change their observable
behavior. Password change samples the application clock once on every entered
transaction, including Token origin.

### Durable invariants

- Old password authentication fails after commit; the winning new password
  succeeds.
- Browser-origin success invalidates the originating old session and every
  sibling; exactly the returned replacement authenticates and accepts its
  returned CSRF value.
- Token-origin success leaves zero browser sessions.
- API-token rows, secrets, scopes, expiry, revocation, and `last_used` policy
  are unchanged. Password change itself performs no token lookup or touch
  beyond authentication already completed by its transport boundary.
- Any error after real DML leaves the old password and all preexisting sessions
  unchanged and leaves no replacement row.
- Returned secrets never survive a failed callback or commit.
- A same-user random collision is detected transactionally before mutation, so
  an originating or sibling identifier can never become the replacement.
  Another user's collision reaches the unique insert and rolls back the
  preceding password update and all-session deletion; every other replacement
  insert failure has the same rollback boundary.

## Exact REST contract

### Provenance handoff

`Handler.Middleware()` records which credential actually succeeded in an
adapter-private Gin/request context value:

- after a valid session and exact CSRF pair, record browser origin plus the
  exact session secret and CSRF candidate;
- after successful Token authentication, record Token origin; and
- never record a value before authentication/CSRF succeeds.

The password handler consumes that value and constructs the corresponding
application credential. It must not infer origin from `Cookie`,
`Authorization`, Principal fields, route, or result expectations. A missing or
invalid context value is an internal adapter-wiring failure: return the generic
HTTP 500 body, call no application service, mutate nothing, and emit no cookie.

Preserve I3 arbitration exactly:

| Presented state                                                           | Winning provenance/outcome                         |
| ------------------------------------------------------------------------- | -------------------------------------------------- |
| Valid session + valid CSRF + absent/valid/invalid/malformed Authorization | Browser session; Authorization is ignored          |
| Valid session + invalid CSRF + valid Token                                | 403; no Token fallback and no application mutation |
| Duplicate `sessionid` cookies                                             | Existing fail-closed response; no Token fallback   |
| Session infrastructure failure + any Authorization                        | Existing 500; no Token fallback                    |
| Unknown/expired/inactive-owner session + valid Token                      | Token                                              |

### `TestPostgresPasswordChangeSerializesWithLogin`

This is mandatory because password change creates a replacement session while
login independently creates a fresh session. I3's reset-wins login regression
and I4's two-password-change race do not prove the opposite lock order or the
final session set when both successful use cases can return material.

Use two pinned connections, explicit preverification barriers, and observed
`pg_locks` contention. Run both orders without sleeps:

1. **Password change wins:** both operations complete their initial password
   verification; password change acquires the advisory lock and is held before
   commit; login is observed waiting; password change commits; login enters,
   rejects the stale verified hash as Unauthenticated, and returns no session.
   Exactly the password-change replacement survives.
2. **Login wins:** both operations complete initial verification; login
   acquires the advisory lock and is held before commit; password change is
   observed waiting; login commits one fresh session; password change then
   revalidates the still-current hash, commits, deletes the old and just-created
   login sessions, and creates its one replacement. Both calls may report
   success at their serialization points, but the returned login session must
   fail afterward and exactly the password-change replacement survives.

one-row session state, replacement CSRF validity, no reusable secret output,
